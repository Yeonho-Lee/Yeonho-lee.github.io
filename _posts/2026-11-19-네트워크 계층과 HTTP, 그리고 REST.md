## 네트워크에는 왜 "계층"이 있을까

초창기에는 컴퓨터끼리 통신하는 표준이 없어서 제조사마다 방식이 제각각이었다. 그래서 **ISO**라는 국제 표준 기구가 통신 과정을 7단계로 나눈 **OSI 7계층**이라는 표준 모델을 만들었다.

다만 실제 인터넷은 이보다 단순한 **TCP/IP 모델**을 기반으로 동작한다. 흔히 5계층으로 나눠서 설명한다.

| TCP/IP (5계층) | 하는 일 | 예시 | OSI 7계층 대응 |
| --- | --- | --- | --- |
| 5. 응용 | 실제 데이터를 주고받는 규칙 | **HTTP**, DNS | 5~7계층 |
| 4. 전송 | 데이터를 빠짐없이, 순서대로 전달 | TCP, UDP | 4계층 |
| 3. 네트워크 | 주소(IP)를 보고 목적지까지 길 찾기 | IP | 3계층 |
| 2. 데이터 링크 | 같은 네트워크 안에서 전달 | 이더넷, Wi-Fi | 2계층 |
| 1. 물리 | 전기 신호, 케이블 | 랜선, 광케이블 | 1계층 |

> 💡 TCP/IP 모델은 원래 4계층인데, 설명할 때 물리 계층을 따로 떼서 5계층으로 나누기도 한다.

프론트엔드 개발자가 직접 신경 쓰는 건 대부분 맨 위 **응용 계층의 HTTP**다. 아래 계층은 브라우저와 운영체제가 알아서 처리해 준다.

## HTTP 요청은 어떻게 생겼을까

HTTP 메시지는 크게 **시작줄, 헤더, 바디** 세 부분으로 나뉜다.

```http
POST /api/students HTTP/1.1
Host: example.com
Content-Type: application/json

{ "name": "홍길동" }
```

- **시작줄** (첫 줄): 어떤 **메서드**(`POST`)로 어느 **경로(엔드포인트)**(`/api/students`)에, 어떤 HTTP 버전으로 요청하는지 적는다.
- **헤더** (`Host`, `Content-Type`): 데이터 형식, 인증 정보 같은 부가 정보를 담는다.
- **바디** (빈 줄 아래): 실제로 보낼 데이터를 담는다. `GET` 요청에는 보통 바디가 없다.

응답도 같은 구조다. 시작줄에 메서드 대신 **상태 코드**가 들어간다는 것만 다르다. `curl -v`를 쓰면 실제로 오가는 요청(`>`)과 응답(`<`)을 그대로 볼 수 있다.

```bash
$ curl -v http://localhost:5173/api/students
> GET /api/students HTTP/1.1          ← 요청 시작줄
> Host: localhost:5173                ← 요청 헤더
> Accept: */*
>
< HTTP/1.1 200 OK                     ← 응답 시작줄 (상태 코드)
< content-type: application/json      ← 응답 헤더
< content-length: 85
<
[{"id":1,"name":"홍길동"},{"id":2,"name":"홍길순"},{"id":3,"name":"김철수"}]   ← 응답 바디
```

> 💡 HTTP에도 버전이 있다. HTTP/1.1, HTTP/2, HTTP/3 순서로 발전하면서 점점 빨라졌다. 특히 HTTP/3은 위 표의 전송 계층에서 TCP 대신 UDP 기반의 **QUIC**를 쓴다.

## REST: 주소와 메서드로 의미를 표현하기

API 설계 방식 중 가장 널리 쓰이는 게 **REST(Representational State Transfer)**다.

REST는 원래 API 작명 규칙이 아니다. HTTP 명세를 만든 사람 중 한 명인 로이 필딩이 2000년 박사 논문에서 "웹이 이렇게 크게 성장할 수 있었던 설계 원칙"을 정리한 **아키텍처 스타일**이다. 무상태성, 캐시 가능성, 균일한 인터페이스 같은 여러 제약 조건으로 이루어져 있다.

API를 만들 때 가장 눈에 띄게 드러나는 건 그중 **균일한 인터페이스**, 즉 **URL로 자원을, 메서드로 행위를, 상태 코드로 결과를** 표현하는 부분이다. 이름의 "Representational"도 여기서 나온다. 학생 자체가 아니라 학생의 **표현**(JSON 같은 형태)을 주고받는다는 뜻이다.

### REST가 없다면

각자 마음대로 URL을 지으면 이렇게 된다.

```
GET  /getStudents
POST /createStudent
POST /deleteStudent?id=3
```

URL마다 동사가 들어가고, 무엇을 하는지 URL 이름을 읽어 봐야 안다. API마다 이름 짓는 규칙도 제각각이다.

### REST라면

REST는 역할을 나눈다.

- **무엇을**: URL에는 **명사**로 자원만 적는다 (`/students`, `/students/3`)
- **어떻게**: 행위는 **HTTP 메서드**로 나타낸다
- **결과는**: **상태 코드**로 알려준다

| 하고 싶은 일 | RESTful 요청 | 성공 시 응답 |
| --- | --- | --- |
| 학생 목록 조회 | `GET /students` | `200 OK` |
| 학생 한 명 조회 | `GET /students/3` | `200 OK` |
| 학생 추가 | `POST /students` | `201 Created` |
| 학생 정보 수정 | `PATCH /students/3` | `200 OK` |
| 학생 삭제 | `DELETE /students/3` | `204 No Content` |

없는 학생을 조회하면 `404 Not Found`, 권한이 없으면 `403 Forbidden`처럼, 응답 본문을 열어 보지 않아도 결과를 알 수 있다.

이 원칙을 잘 지킨 API를 **RESTful하다**고 한다. 규칙이 통일돼 있으니 처음 보는 API도 `GET /lessons/5`가 뭘 하는지 예측할 수 있다.

> 💡 `PUT`은 자원 전체를 갈아끼우고, `PATCH`는 일부만 수정한다.

> 💡 엄밀히 따지면 실무의 "REST API"는 대부분 위의 URL, 메서드, 상태 코드 규칙까지만 지킨다. 응답 안에 "다음에 할 수 있는 행동"의 링크를 담는 **HATEOAS** 같은 제약은 거의 지키지 않아서, 필딩 본인은 "그건 REST가 아니다"라고 말하기도 했다. 그래서 정확히는 "REST 스타일을 빌린 HTTP API"에 가깝다.

## 그런데 지금 프로젝트는 Remote Functions를 쓴다

원래대로라면 SvelteKit에서도 `+server.ts`에 메서드별 핸들러를 만들고, 프론트에서 `fetch`로 URL과 메서드를 직접 맞춰 호출해야 한다.

```ts
// src/routes/api/students/+server.ts
import { json } from '@sveltejs/kit';
import { db } from '$lib/server/db';
import { students } from '$lib/server/db/schema';

export async function GET() {
	const list = await db.select().from(students);
	return json(list);
}
```

```ts
// 컴포넌트에서
const res = await fetch('/api/students');
const list = await res.json();
```

학생 한 명을 다루는 `/api/students/3` 같은 경로는 폴더를 하나 더 만들고, 위 REST 표처럼 메서드마다 함수를 export한다.

```ts
// src/routes/api/students/[id]/+server.ts
export const GET: RequestHandler = async ({ params }) => {
  const [found] = await db
    .select()
    .from(students)
    .where(eq(students.id, Number(params.id)));
  if (!found) error(404, '학생을 찾을 수 없습니다');
  return json(found);
};

export const PATCH: RequestHandler = async ({ params, request }) => { /* 수정 */ };
export const DELETE: RequestHandler = async ({ params }) => { /* 삭제 */ };
```

요청을 보내 보면 메서드와 상태 코드가 REST 표대로 움직인다.

```bash
$ curl -i -X PATCH /api/students/3 -d '{"name":"김영수"}'   # HTTP/1.1 200 OK
$ curl -i -X DELETE /api/students/4                        # HTTP/1.1 204 No Content
$ curl -i /api/students/4                                  # HTTP/1.1 404 Not Found
$ curl -i -X PUT /api/students/3                           # HTTP/1.1 405 Method Not Allowed
                                                           # allow: GET, PATCH, DELETE, HEAD
```

`PUT` 핸들러는 만들지 않았기 때문에 SvelteKit이 `405 Method Not Allowed`와 함께, 쓸 수 있는 메서드 목록을 `allow` 헤더에 담아 돌려준다.

지금 프로젝트에서는 이 대신 **Remote Functions**를 쓰고 있다.

```ts
// src/routes/students.remote.ts
import { query } from '$app/server';
import { db } from '$lib/server/db';
import { students } from '$lib/server/db/schema';

export const getStudents = query(async () => {
	return db.select().from(students);
});
```

```svelte
<script lang="ts">
	import { getStudents } from './students.remote';
</script>

{#each await getStudents() as student}
	<p>{student.name}</p>
{/each}
```

URL을 정하고 메서드를 고르고 응답을 JSON으로 바꾸는 일을 SvelteKit이 대신 해준다.

### REST가 아니라 RPC

여기서 재미있는 점이 있다. Remote Functions는 REST가 아니라 **RPC(Remote Procedure Call)** 방식이다. REST가 "어떤 **자원**에 어떤 **행위**를 할지"를 URL과 메서드로 표현한다면, RPC는 그냥 "서버에 있는 **이 함수를 불러줘**"라고 요청한다. 앞에서 본 `/getStudents` 같은 동사형 URL이 사실 RPC 스타일이다.

실제로 SvelteKit 내부 코드를 보면, Remote Functions는 자원 이름이 아니라 함수 ID로 만든 경로 하나를 호출한다.

| Remote Function | 실제 HTTP 요청 |
| --- | --- |
| `query` | `GET /_app/remote/{함수 ID}?payload=...` |
| `query.batch` | `POST /_app/remote/{함수 ID}` |
| `command` | `POST /_app/remote/{함수 ID}` |
| `form` | `POST /_app/remote/{함수 ID}` |

학생을 조회하든 추가하든 URL에 `/students` 같은 자원 이름은 없고, 메서드도 사실상 GET(읽기)과 POST(그 외) 두 가지만 쓴다. `PATCH`, `DELETE`를 고민할 필요가 없는 대신, RESTful하지는 않은 거다.

`getStudents`를 직접 `curl`로 불러 보면 이렇다.

```bash
$ curl -v http://localhost:5173/_app/remote/1210p81/getStudents
> GET /_app/remote/1210p81/getStudents HTTP/1.1
< HTTP/1.1 200 OK
< content-type: application/json
{"type":"result","result":"[[1,4,7],{\"id\":2,\"name\":3},1,\"홍길동\", ...]"}
```

`1210p81`은 `.remote.ts` 파일마다 붙는 해시고, 뒤에 **함수 이름**이 그대로 붙는다. "`getStudents` 함수를 불러줘"라는 RPC 요청인 셈이다.

[지난 글]({% post_url 2026-11-19-네이버에서 검색 한 번 하면 무슨 일이 일어날까 %})의 `searchStudents('홍')`처럼 인자가 있으면 `payload`에 실린다.

```
GET /_app/remote/1210p81/searchStudents?payload=WyLtmY0iXQ
```

`WyLtmY0iXQ`는 인자 `'홍'`을 JSON 비슷한 형식(`["홍"]`)으로 바꾼 뒤 URL에 쓸 수 있게 base64로 인코딩한 값이다. 응답의 `result`가 평범한 JSON이 아닌 것도 같은 이유다. SvelteKit은 `Date`, `Map` 같은 값도 주고받을 수 있도록 [devalue](https://github.com/sveltejs/devalue)라는 형식으로 직렬화한다.

에러를 다루는 방식도 다르다. 문자열 대신 숫자를 인자로 보내서 검증에 실패하게 만들어 보면:

```bash
$ curl -i "http://localhost:5173/_app/remote/1210p81/searchStudents?payload=WzEyM10"   # 인자: 123
HTTP/1.1 200 OK
{"type":"error","error":{"message":"Bad Request"},"status":400}
```

HTTP 상태 코드는 `200 OK`인데, 진짜 결과(`400`)는 **바디 안에** 들어 있다. REST에서는 상태 코드 자체가 결과를 말해주지만, 여기서는 HTTP를 "함수 호출 결과를 실어 나르는 통로"로만 쓴다. 이것도 RPC다운 모습이다.

그렇다고 HTTP가 사라진 건 아니다. 개발자 도구의 네트워크 탭을 열어보면 위처럼 `/_app/remote/...`로 HTTP 요청이 오가는 걸 볼 수 있다. 우리가 직접 신경 쓰지 않아도 될 뿐이다.

## 마치며

HTTP와 REST를 알고 나니 Remote Functions가 무엇을 대신해 주는지, 그리고 REST와 무엇이 다른지 더 잘 보였다. 다음 글에서는 요청의 종착지인 **DB**, 그중에서도 지금 프로젝트에서 쓰는 SQLite와 Drizzle 이야기를 해본다.
